# Shared layers

> Part of the Distrilight tools suite — start from `CLAUDE.md` in the repo root, which
> holds the hard rules, the map of the repo and how to check a change. This file is
> the depth for one tool: read it before you change one of the shared files — `pdf-huisstijl.js`, `armatuur-groepen.js`, `zoeken.js`, `spec-lezer.js`, `info-teken.js` — or the presenter PDFs.

## Shared scripts

**`info-teken.js`** is the shared **information icon**: a small ⓘ that shows a balloon on hover or focus and opens the same text large in a new tab on click. `InfoTeken.zet(kop, {titel, tekst, lijst, beeld, bijschrift, breed})` appends one, `InfoTeken.maak()` returns the element, and `InfoTeken.scan()` turns `<span data-info="…" data-info-titel="…">` into icons — that scan runs by itself once the page has loaded, so a plain-HTML use needs no JavaScript at all. Every tool in the suite loads the file, so the function is available everywhere; it is used for the explanation of the light apertures in `bandrasters.html` and for the drawing plus application text behind every article in "Adapters & overig" in `index.html`. Three things it does deliberately: everything is escaped and rendered as text (a half HTML editor inside a tooltip only yields broken balloons), the balloon is a single element on `<body>` rather than one per icon (a card or table cell with `overflow` would otherwise clip it), and the new tab is a blob URL rather than `document.write` into a fresh window, which is no longer allowed everywhere from `file://`. It brings its own stylesheet, so adding it to a page is one `<script src>` line.

**`zoeken.js`** is the shared **search helper**, loaded by the railtool, the armaturenboek and the vergelijker: `zoekNormaal()` (case, accents, `60 x 60`/`60×60`, `4000 K`, `3 m`), `zoekWoorden()`, `bevatWoord()` (a word with a digit may not start right after another digit, so `15w` does not find 115W), `maatLezingen()` (`600x600` is also 60x60, `120x30` also 30x120), `tekstPast()` (every word, in any order, or one of its synonyms), `codeSleutel()`/`lijktCode()` for article numbers, and `bewerkAfstand()`/`besteSuggestie()` for a typo suggestion that is never applied silently and never offered for a number (`bewerkAfstand()` counts two swapped neighbouring letters as one edit, the most common typo). `armatuur-groepen.js` uses `bewerkAfstand()` for its own, stricter suggestion, so the armaturenboek loads this file too. What a tool searches and how it ranks stays in the tool; `controleer-suite.mjs` fails when a page grows its own copy of one of these functions or uses them without loading the file.

**`spec-lezer.js`** holds the paste-and-parse machinery shared by the vergelijker and the DLC tool (`SpecLezer.maak({veldmap, sectie, kop, fragmenten, vrijeTekst, eenheidUitLabel})` → `lees(tekst)` → `{uit, herkend, onbekend}`). It handles `Label: waarde`, a label with its value on the next line, `Groep: Label: waarde` from bestekteksten, comma-separated one-liners, HTML entities, and units carried in the label. Two details that a supplier sheet quickly runs into: a line is only cut at a comma when the label **behind** it is one the veldmap knows (`splitsLabelparen()`), so a value like `B10: 30, B16: 47, C10: 50, C16: 80` stays one entry instead of falling into four; and whether a line is a value rather than a label is judged on the **cleaned** label, so `ULOR (<1%)` is a label despite the digits inside its bracket. **A sales paragraph puts those pairs behind a full stop instead of a comma**, in running prose (`… may not burn at a speed of more than 50mm per minute. Light color temperature: 4000K Cool White`), so the same cut is made at a sentence end — under the same proviso, which is what does the work: only where a **known** label follows, so an ordinary sentence stays whole and the description survives. And a labelled value ends at the end of **its own** sentence (`knipNaZin`): `weight: 2.2kg. For using EM kits 0046600-01 please order connector 0047523.` used to put that whole ordering note in the weight field. What followed is not dropped — it becomes a line of its own and lands in `onbekend` if nothing matches it. Both cuts need whitespace after the full stop, so `2.2kg`, `50.000 uur` and `L80/B20>50,000` stay intact, and a table has no sentences so nothing there changes. `ontHtml()` strips only what really looks like a tag — `<` followed by a letter or a `/`, with no second `<` inside — because a plain `<[^>]*>` ate `UGR<19, Ra>80` down to `UGR80`. It never guesses: anything it cannot place lands in `onbekend` so the tool can show it. A second pass, `fragmenten`, handles the sheet that arrives as **values only** — one line, not a single label: `600x600 mm, Staal, Wit, Voedingsunit met DALI-interface, 3600 lm, 26 W, 140 lm/W, 4000 K, UGR19, IP 20/44 | Bescherming tegen vingers, IK02 | 0,2 J`. There is nothing to split into label and value there — what a fragment means is inside the fragment itself — so that round holds patterns instead of labels, with the unit or the shape as the anchor (`lm` can only be luminous flux, `IK02` only impact resistance). `splitsFragmenten()` cuts on comma, semicolon and pipe, but **not inside brackets** (`(0.38, 0.38) SDCM ≤3` is one value) and **not between two digits** (`0,2 J` is a number), and it drops a trailing full stop — these rows are often typed as a sentence, and `IK08.` matches nothing. Only a **tab** disqualifies a line as a pasted table row: a run of spaces does that just as often by accident (`… mm,  IP65`), and the thresholds below stop a real table row anyway (it yields one fragment, not three). A pattern may say `voeg` (a second hit joins the first: "Insteekconnector, 4-polig") or `wint` (more specific overwrites: RAL9003 over "Wit"); both only within that round — a real label always wins. The round hangs on `fragmentStukken()`, which sets five thresholds to keep an ordinary sentence with commas from being torn apart instead of staying the description: three fragments or more, barely any colons, no fragment longer than 60 characters, **half** the fragments recognised, and at least **two** of them matched by a pattern that is anchored (`^`) — i.e. where the whole fragment is the value. That last one is the discriminator that actually works: `prisma` and `recessed` both match inside "Recessed downlight, round, with a micro-prismatic diffuser for offices", but neither covers a whole fragment, so that line stays a description. `vastAnker()` reads the anchoring off the regex so it can't drift from the pattern; a pattern may override it with `anker`. A line that clears that bar is skipped by the normal round — as a heading line too, because otherwise the whole row would land in the sheet as the description, which was exactly the complaint. A third pass, `vrijeTekst`, handles suppliers who send a sales paragraph instead of a table ("… Vijf jaar garantie. 13w 4000k 1900lm; lengte 600mm; Diameter 60; 0,5kg ; DALI"): there the **unit is the anchor**, not the label — `lm` can only be luminous flux, `kg` only weight — so a bare number without a unit is deliberately left alone rather than guessed at. It only fills fields the first pass did not — a real label knows more than a pattern. **The vergelijker has its own table of these** (`VRIJE_TEKST`, beside `FRAGMENTEN`), because a bestekpositie arrives as prose as often as as a table and half the specification then sits mid-sentence: `Low glaring UGR<19`, `Ra80 typical`, `100-degree beam angle`, `DALI-2 dimmable`, `White color frame`. The bar is higher than in the fragment round, since a pattern may strike inside a sentence here: only what can mean one thing, and `lm/W` is excluded from luminous flux because that is the efficacy. When it finds something the prose lines are dropped from `onbekend` (a sales text is expected to be prose; only lines with a colon are a visible attempt at a label) — but **only when the running text is really the source**: if the ordinary round filled more fields than this one, the paste is a sheet with a few loose sentences in it, and those sentences are exactly what is worth reading. `eenheidUitLabel:false` switches off the unit-append rule for sheets whose labels already carry the unit. **Supplier sheets come in Dutch and English**, often half and half, so the vergelijker's `SECTIE` and `VELDMAP` carry both spellings. The section headings are not cosmetic: `dimbaar` is keyed on `Type` **within** a control/dimming section, so without `control|dimming` as a heading word "Trailing edge" lands in the sheet's Type column instead. A word only goes into `SECTIE` if it cannot plausibly be a *value* as well — a value line that reads as a heading is not consumed by the label above it. **A bestek is not a supplier sheet**, and its wording is its own: `Fabricaat` for the make, `Locatie` for where it hangs, `Schakeling` for the control, `Kleur temp` abbreviated, `Lumen` where a data sheet writes `Lichtstroom`. Those spellings are in the `VELDMAP` alongside the supplier ones. Two of them were structural rather than a missing synonym: **Leverancier and Toepassing are rows on the comparison sheet that had no label at all**, so they could only ever be typed by hand however the paste was worded — they now have an entry and a line in `naarBladvelden()`. `Uitvoering` and `Reflector` are read into `_uitvoering` / `_optiek`: they have no row on the sheet (adding one would leave it empty for 400 other families) but a field that is read is not reported as unrecognised, which is what sends someone hunting for a mistake that isn't there.

## The fixture row — `armatuur-rij.js`

**A typed article code fills in the full name** (October 2026, asked for by the user): `armNaamVeldUitCode()` looks the code up in `catalogus-data.js` (`catalogusNaam()`, exact match only — case and surrounding spaces do not matter, a near code is another article and gets nothing) and fills the name field when it is empty, or when the name came from the catalogue for an earlier code (`naamUitCatalogus` on the row); a name the user typed or changed is never overwritten. When the new code is not in the catalogue and the name belonged to the previous code, that name is cleared, so a name never stands beside a code it does not belong to; with no name the tool says the code is not in the catalogue and rings the name field. The name goes in through the same `change` as typing, so recognition and a series choice treat it exactly the same. Accessory rows do the same. `catalogus-data.js` is generated from `vergelijker/data/bron/catalogus.csv`, `spots.csv`, `wandarmaturen.csv`, `opbouwarmaturen.csv` and `noodverlichting-skyline.csv` by `node tools/maak-catalogus-data.mjs` (6145 codes; double spaces in the source become single; a code in more than one keeps the first source's description, the catalogue's). The other four are inside sales' lists of all spots, all wall fixtures, the surface-mounted Valento and — later that month — the emergency lighting with the whole Skyline range (October 2026; without the phased-out spots, and without the 186 Dura rows of the wall list, which were all in the catalogue already), for this lookup only — see `docs/vergelijker.md` for why the vergelijker does not read them. They took the Zena, the Ario 1-fase railspot, the Waldo, Pareto, Qube, Valento and some 570 others from nothing to a name; the emergency list (250 rows: Dot, Dot Plus, DotXL, Dot IP65, Juno, Maximus, Norma, Picto, UNI, their batteries and converters, four DLC emergency fixtures — whose codes are names with spaces, which the lookup takes as they are — and 197 Skyline luminaires, accessories and parts) added 248 more, the other two were in the catalogue already with the same description. Measured on recognition: all Skyline rows get the Skyline sheet, the Dot range its own sheets (the four DotXL ones only with the joined-spelling search term), Juno and the DLC fixtures none — there is no sheet for them; on a real project list the Excel check went from 7 to all 15 of its Pragmalux rows, every one equal to the catalogue. **The catalogue is not complete**: among the Pragmalux codes, 58 base articles (seven digits, no suffix) are missing while a variant of them is there — PRX-Line G2, a number of bandrasters — so their codes find nothing until a fuller export is added (`knip-export.py --aanvullen`). The Dura-M and Dura-S used to be the first example (only the Casambi versions were in, so the 1084459-SN this feature was asked for found nothing); in October 2026 inside sales supplied the whole Dura list, 208 articles of which 192 were new, and every one of them gets the Dura sheet. `controleer-logica.mjs` checks the lookup and the rules; `controleer-suite.mjs` the fingerprint and that a tool using it loads the file.

The armaturenboek and the railtool make the same book — a row per fixture, a presenter per type, an armaturenlijst and a code stamped on each presenter — and each used to do it its own way. They had drifted: the railtool had no upload button for an unrecognised type, no Mondial choice, one stamp style at a different spot, a list grouped by type with the unrecognised rows at the bottom, and no arrows. Everything that should be the same now lives in `armatuur-rij.js`, a plain script with top-level functions (like `armatuur-groepen.js`, so `controleer-logica.mjs` can cut them out):

- `armGroepVanRij(s, armId, special)` — which presenter a row gets: an uploaded PDF (`sp<armId>`) on any row first, then `s.groep` (a manual choice; `'-'` is none), then `matchArmGroep()` on the name. The tool passes `special`, because which code field counts differs (the railtool reads the DALI code in DALI mode).
- `armTypeOnbekend()` — whether the upload button shows; it ignores the uploaded PDF on purpose, or the button would vanish once used.
- `armRijDelen(o)` — the label (recognised type, the series choice, the typo suggestion), the upload button with its ×, the stamp toggle and the ↑/↓ arrows as DOM parts; the tool builds its own row around them and passes `opWijziging` (`refresh` or `updateSummary`). It owns the name field's listeners, including `armKeuzeBlijft()`.
- `armWisselRijen()` — swaps the contents of two slots, and an uploaded PDF with them; `armVolgBijwerken()` disables the first ↑ and the last ↓.
- `armBoekGroepen(boek)` and `stempelPresenter()` — per presenter the unique codes (stacked, one per line), colour, style and whether it is a special, and the stamp itself at the measured spot, shrinking rather than shifting when a code is too wide. A special (an uploaded PDF, usually a DLC sheet) has its own spot, `STEMPEL_SPECIAL`, clear of the DLC header band and logo block, and defaults to black — see `docs/armaturenboek.md`.
- `armSlotLeeg(s)` — whether a row counts: anything filled in (code, name, article code or DALI code, a quantity, an accessory), whitespace not counting. Both tools use it for the book, the list and the warnings, so a row without a quantity is in both or in neither.
- `armAccessoires(s)` and `armAccessoireDelen(o)` — the accessories of a row (`s.accessoires = [{code, name, qty}]`: a surface-mounting set with a Mondial Opbouw, a pendant set): their own article code and name, **no CODE of their own and no presenter**. `armAccessoires()` keeps the ones with a code or a name; `armAccessoireDelen()` gives the "+ Accessoire" button for the row and the list of sub-rows under it (article code, name, an optional quantity, ×). The sub-rows run in columns with the row — the label where the CODE is, then article code, name, quantity under quantity and × under the button — so the button and the × share one fixed width (`--acc-knop`); a tool with other field widths sets `--acc-inspring`, `--acc-label` and `--acc-code`. They are part of the row's state, so ↑/↓ moves them along and saving keeps them without anything else knowing.
- `armLijstKolommen(rijen, artikel, oms)` — the armaturenlijst's columns and values; Code and Aantal drop when no row (and no accessory) has one. `regels` is what the table draws: each fixture with its accessories directly under it, the Code cell empty (they belong to the code above) and the quantity only when one was filled in — empty is not 0. An article code that was not filled in stays empty, for a fixture as for an accessory; the tools used to print `volgt` there, and the user asked for an empty cell. An accessory is marked `vervolg`, and `tableRow(T, vals, {vervolg:true})` gives it the shade of the row above instead of the next one in the alternation, so fixture and accessories read as one entry.
- `armEigenPresenters()` — every uploaded PDF, for "Project opslaan".
- **The remark on the presenter** (`s.opmerking`, October 2026: "bij opmerkingen deze in het klein in het rood op de presenter geplaatst worden. dit moet mooi aligned zijn met waar de code stempel ook komt"). It comes from column L of an Excel list or is typed: a pencil inside the CODE field (shown while the row has a stamp and no remark; inside the field because a "+ Opmerking" button beside the stamp pushed the railtool's rows onto two lines at 1280 px) opens a sub-row "↳ opmerking" under the fixture, indented like an accessory, with × to remove it. `armBoekGroepen()` gives per code its remark (`opmerking`, parallel to `code`; different remarks for one code joined with " · ", a remark on a row without a code at the end with an empty code), and `stempelPresenter(…, opmerkingen)` draws each one in red, 7.5 pt, **left of its code on the same baseline, all remarks ending on one line a gap (9 pt) left of the widest code** — two clean columns. Within the same safe width as the codes (250 pt); a longer remark wraps (the codes below move down by the extra lines) and shrinks by half points to 6 pt if it would take more than three lines. Two reds (`STEMPEL_OPMERKING`): the PDFs' red #D6362B reaches only 3.4:1 on the Pragmalux presenters' dark header, so a white stamp gets #FF4B3E (5.0:1); a black stamp or a group with its own stamp colour (a light header) keeps #D6362B (4.7:1 on white). Without remarks every stamp is drawn exactly as before — the PDF regression stays byte-identical. `armSlotLeeg()` counts a remark, so a row with only a remark is not overwritten by an import.
- **Which columns the armaturenlijst has** (October 2026: "ik wil wel de mogelijkheid per kolom … of ik die in de pdf wil hebben of niet"): `armKolomKeuze(o)` gives the ticks *Code*, *Artikelcode*, *Aantal* (`ARM_LIJST_KOLOMMEN`) under "Armaturenlijst in de PDF", greyed while the list itself is off; the choice is `st.lijstKolommen` (only `false` counts, so an old project has everything on — and restoring one resets the choice instead of keeping the previous project's), saved with the project, and `armLijstKolommen(rijen, artikel, oms, keuze)` leaves an unticked column out, its width going to Omschrijving, which is always there. Code and Aantal still drop by themselves when no row has a value.

Like `info-teken.js` it brings its own stylesheet for those parts; the tools keep only the widths of their own fields. `controleer-suite.mjs` fails when either tool grows its own copy again or uses the file without loading it, and `controleer-logica.mjs` holds the rules.

## Fixtures from an Excel list — `armaturen-excel.js`

**The fixture rows can be filled from an Excel list** (October 2026, at the user's request: "ik wil dat je een excel kunt inladen en dat hij vanuit daar het armatuurcode (kolom A), artikelcode (kolom I) en omschrijving (kolom J) invult"; then, with the list inside sales actually makes — "zo zullen we hem dus ook gaan aanleveren" — the total quantity, accessories and the remark). Both tools have a button "Armaturen uit Excel inladen" above the fixture list; `ArmaturenExcel.koppel({knop, bestand, regelIds, regel, nieuweRegel, artikelVeld, herbouw, opWijziging})` wires it, and the tool passes how its rows are kept (the railtool's `artikelVeld` is `codeDali` in DALI mode, so the codes go into the field that is on screen).

**The list's layout** (their template): three header rows — *Armatuurcode / Aantallen / Leverancier / merk / type / Voorbeeld / ARTIKELCODE / OMSCRHIJVING* (sic) */ VOORBEELD / OPMERKINGEN*, then the rooms (KANTOOR, HAL), then the floors (BG, V1, V2) and *TOTAAL* — and one row per fixture code. **Five columns are read, the rest is ignored** (`EXCEL_KOLOM`): A the code (the row's CODE, `aanduiding`), **F the total quantity** (B–E are the quantities per room or floor), I the article code, J the description, **L the remark**. A row with nothing in I and J does not count (an empty row, a title, a sub-heading, a template row with only a 0 in the total column), nor does a header row (`EXCEL_KOPWOORD`: *ARTIKELCODE* and the like in I or J). F becomes the quantity when it is a positive number (text, empty or 0 → 0). **Accessories sit on their fixture's row, with a + between the article codes** — `1000947-OS + 1000282` is the panel with emergency kit 1000282 — and the descriptions in J the same way. The codes are split on every +; the description is split by `excelDelen()`, because a name can contain a + itself ("2-CCT + bewegingssensor", "UGR<19 +Osram Driver"): of all ways to cut J at its + signs, the one whose pieces differ least from the catalogue names (words in one and not the other) wins; with no catalogue name to go by, the cut with the most pieces and the boundaries furthest back (a fixture has a + in its name more often than an accessory); fewer pieces than codes leaves the last descriptions empty. Each accessory gets the row's quantity: 8 in the total column means eight panels, each with its kit (also what the railtool's order list needs). The rows go into the **empty rows after what is already there** — nothing is overwritten, and loading twice adds the list twice.

**The name comes from the catalogue, as when typing** (`catalogusNaam()`), per article — fixture and accessories alike; **the description in the list is the check**. `excelVergelijk()` compares the two word for word, ignoring only whitespace (a capital or a punctuation mark is a difference — "1 op 1" was the user's word): equal → the catalogue name; different → the catalogue name for now and a **choice window** (`<dialog>`) with one row per differing article (an accessory is marked as one), the differing words marked (`woordVerschil()`, a word-level longest common subsequence, so one changed character in a 150-character description stands out), buttons "Overal de catalogus" / "Overal de Excel-lijst", and *Overnemen* disabled until every row is chosen; Esc does not close it. An article code that is not in the catalogue takes the description from the list (nothing has checked it, so the closing note is a *let op*); with neither, the name stays empty. A kept Excel description is the user's own name (`naamUitCatalogus` empty), so a later change of article code leaves it alone; a catalogue name follows the code, as it does when typed. The closing note counts what happened per kind. *Special* in column I works as typed: the row gets the upload button for its DLC sheet. **Measured on the user's example** (4 codes): CODE A 5×, CODE B 8× with 1 accessory and the remark "Niet IK10", CODE C 4× with 2 accessories, CODE D a special; the three fixtures equal to the catalogue, the two accessory codes (1000282, 9322219-300) not in it. On an older project list of theirs (28 rows) only 7 of the 17 Pragmalux rows could be checked: the Ario 1-fase railspot, Valento, Zena and Waldo are not in the catalogue at all — a fuller export (through `knip-export.py`) fixes that.

**Reading**: a `.xlsx` is a zip of XML, read without a library — `excelRijen()` walks the zip's central directory, inflates with `DecompressionStream('deflate-raw')` (stored entries as they are), takes the **first sheet** via `workbook.xml` and its rels (Excel keeps `sheet3.xml` as the file name when that sheet is dragged to the front), and reads shared strings (rich text in runs, the phonetic `<rPh>` left out), inline strings, numbers and formula results. A `.csv` (semicolon or comma, quotes, `""`, BOM; UTF-8 with a windows-1252 fallback, as Excel writes it) works too; an old `.xls` gets a message to save it as `.xlsx`, and a broken zip says so instead of a bare `TypeError`. A project file saved while the window was open carries the window in its HTML; it is removed when the page has been read (it sits after the scripts, so not before `DOMContentLoaded`).

**Checked**: `controleer-logica.mjs` reads `tools/proef-armaturen.xlsx` (made with openpyxl by `tools/maak-proef-armaturen.py` in the layout of their template: the three header rows, quantities per room and a total, inline strings, a number as article code, rich text in one cell, a sub-heading, accessories with a + — with and without spaces, behind a name that has a + itself — a special, template rows with only a 0, a second sheet) and a zip built in the check the way Excel writes (shared strings, runs, `<rPh>`, a formula with its cached total in F, a remark in L, a first sheet that is `sheet3.xml`, half stored and half deflated), plus a `.csv`, the quantity rule, the cutting of J and the comparison rules — every case mutation-tested. The customer's own lists are not in the repo. `controleer-suite.mjs` fails when a page uses the file without loading it (or without `armatuur-rij.js`, `catalogus-data.js` and `melding.js`, which it leans on) or grows its own copy.

## Contact persons — `contactpersonen.js`

The armaturenboek and the railtool both show, on the introduction page under the briefing (see `briefing.js` below — the railtool without the briefing puts them at the top of that page), the chosen projectuitwerker, accountmanager and commerciële binnendienst under "Contactgegevens", and the blue "Onze specialist" card for a projectuitwerker with a personal note. Everything that should look and behave the same is in `contactpersonen.js`: the measurements (`CONTACT`, read off "Contactgegevens - Update sep 2026.pdf" and the example page), `medewerkerVan()` / `contactPersonen(keuze)` / `contactRegels()` / `specialist(keuze)`, the three selects (`contactKeuze(vak, keuze, opWijziging, idVoorvoegsel)`, which empties its container first because a saved project already carries the baked selects) and the drawing (`tekenContactpersonen(HS, keuze, plek, eersteGat, stand)`, where `plek` reads and sets the tool's own `y` so `need()` sees the same position, and `stand` says how tight the white above the card is and at what scale the card is drawn — `kaartMaten(s)` scales everything inside it, photo, type and padding, and keeps its width, so its edges stay in line with the briefing; see the one-page rule below). The data is `medewerkers.js` and the photos `medewerker-fotos.js` (see `docs/armaturenboek.md`). Like the other shared files it brings its own stylesheet for the selects, `controleer-suite.mjs` fails when a tool grows its own copy or uses it without loading it, and `controleer-logica.mjs` holds the rules.

## The introduction page — `briefing.js`

The page directly behind the cover — "Briefing" (De vraag in the grey quote block, Wat wij bieden, Wij leveren) with the contact persons under it — is **the same page in the armaturenboek and the railtool**, drawn by the same code. Until October 2026 the briefing lived in `armaturenboek.html`, so the railtool's introduction page carried only the contact persons; the user asked for the railtool's projectboek to get exactly the armaturenboek's page. `briefing.js` now holds all of it: the measurements (`BRIEF`), the sources (`BRIEF_VELDEN`) and the text per soort opdracht (`briefInhoud(keuze)` and its helpers), the panel block (`briefingKeuze(vak, keuze, opWijziging, idVoorvoegsel)` — the two soort buttons and the four source fields, emptying its container first for the same reason as `contactKeuze()`; `briefingStand(keuze)` for the line in the closed block's head), the two warnings (`briefingWaarschuwing()` for the summary, `briefingExportMelding()` for the list before the PDF — both only about the project name, the one placeholder left) and the drawing (`tekenIntroductie(HS, keuze, plek, metBriefing)`: section, header, briefing, then `tekenContactpersonen()` from `contactpersonen.js`). Every function takes the tool's state as `keuze`; a state without `soort` (a railtool project from before) is a lichtberekening, as the panel shows it. It brings its own stylesheet for the block (`.brief-vouw`, `.brief-soort`, `.brief-veld`, `.brief-tekst`). **The text can be edited** (October 2026: "een tekstvak met alle tekst waar ik kan weghalen en aanvullen", for a project that is not standard). Under the four source fields, "Briefingtekst zelf aanpassen" opens one textarea holding the whole text as `briefTekst(briefInhoud(keuze))` writes it — plain text with a few marks the page reads back (`briefUitTekst()`): the first paragraph is "De vraag" in the grey block (every line starts a new line there), a blank line starts a paragraph, `**…**` is bold, a line starting with `- ` is a bullet, and a whole-bold line ending in a colon that opens a paragraph is a heading (in capitals the small one, as DISCLAIMER). The spacing comes from the design's own gaps — after the block `naBlok`, after a heading `naKop` (`naDisclaimer` after the small one), a new paragraph `naWit`, the first bullet under a line `naLeveren`, otherwise a line — so every standard text read back gives the same lines at the same distances (`controleer-logica.mjs` checks five cases), and `briefIntroInhoud()` uses the standard itself when the text is unchanged, empty or switched off: the page stays byte-identical. The state is `keuze.briefEigen` / `keuze.briefTekst`, saved with the project; switching off keeps the text, "Standaardtekst terugzetten" regenerates it (after a confirm when there is text to lose), and restoring an older project resets both. The edited text no longer follows the project name or the sources — the panel says so — and the placeholder warning then only fires for a `[projectnaam]` still in it; the block's summary line says "eigen tekst". Measured after the move: the armaturenboek's page renders byte-identical to before in three cases (lichtberekening with bestek, drawings and three contacts; vergelijking with three kinds of source; nothing filled in), and the railtool's page byte-identical to the armaturenboek's in the same three. `controleer-suite.mjs` fails when either tool grows its own copy or uses it without loading it; `controleer-logica.mjs` checks the text.

**The introduction page with a briefing is always one page** (October 2026: on a long briefing — long document names, a vergelijking with its disclaimer, three contacts — "Onze specialist" moved to a page of its own, which the user wants never to happen). Before drawing, `introStand()` measures the page *dry* — the same drawing code (`tekenBriefing()`) with a drawing layer that draws nothing and never breaks a page; its `need()` only records how far the page would have to run, which is exactly the test the real `need()` makes, so what fits dry never breaks for real — and takes the first stand of `INTRO_STANDEN` that fits: as designed; less white above "Onze specialist" (what the tool already did); also less above "Contactgegevens" (`CONTACT.kopGatKrap`); then **the blue card smaller**, in steps of 5% down to three quarters (`kaartMaten()`); and only then the briefing text, to 80% (`briefMaten(t)`: type, line spacing and the grey block with its quote marks; edges, widths and the heading stay). Beyond that — a custom text of a page or more — the text keeps shrinking in 5% steps until it fits (never below `INTRO_TEKST_MIN`, 30%), and whenever the text is below 100% the tool says so in a note (`introStandMelding()`), since the text is then really too long. The railtool without briefing (contacts only) is never in danger and stays as it was. Measured with the user's own page (vergelijking, Bijlage 3 / Bijlage 5 / the e-mail, Karlijn Lemmens, Luuk Eerden, Christophe Canoy): the specialist was on page 3; now everything is on page 2 at the third stand with the card at 85% and the text at full size — in both tools. A page that fitted already is unchanged (whole books compared on content, armaturenboek and railtool without briefing). `controleer-logica.mjs` runs the real choice and drawing code with a rough text measure: for four cases the chosen stand never breaks a page and no earlier stand would have fitted, every length of briefing from one sentence to a full page (with and without the card, 180 cases) stays on one page, the stands run from loose to tight, and scaling keeps the edges; eight deliberate faults, all caught.

## Total project book — `lichtplan.js`

The armaturenboek and the railtool can both make a **totaal projectboek**: the user picks the lichtplan as a PDF and it goes into the book directly after the introduction — or after the cover when there is none (the railtool only has an introduction page with contact persons) — behind the chapter page "Lichtberekening" (`presenters/lichtberekening.js`, the supplied design). `lichtplanDelen(naIntroductie, eigenTotaal, metLichtplan)` returns the tool's own pages with those two parts slid in; each tool appends its presenters (`boekDelen()` in the armaturenboek, `railBoekDelen()` in the railtool). **Since October 2026 the lichtplan can be several PDFs** (a plan per floor, a separate report): they all go behind the one chapter page, in the order of the list in the block. `st.lichtplan` is then a list `[{naam, paginas}]`, or null when empty so `if(st.lichtplan)` keeps meaning "there is one"; a project from before has a single `{naam, paginas}` and `lichtplanLijst()` reads both (checked in `controleer-logica.mjs`). `Lichtplan.koppel({st, knop, bestand, lijst, overzicht, opWijziging})` wires the block — add one or more at once (the file input is `multiple`), ↑/↓ for the order, × per PDF, the name and page count per row and the red "not loaded any more" state per row; a file whose name matches a row that is not loaded any more fills that row, and the identical file chosen twice is skipped with a note. An **already saved project file** carries the old markup and inline code (a name and a × for one lichtplan) but loads this file from the install folder, so `koppel()` without `lijst` hides those two and puts the list above the button in a box with a fixed id (no duplicate on the next opening); measured with the previous armaturenboek: two PDFs in, both in the book, saved and reopened with one list. The block brings its own stylesheet; `Lichtplan.pdf` / `zetPdf()` for the project payload (a list of base64 strings in the order of the list, null for one not loaded; `zetPdf()` also takes the single string of an older payload), `ingeladen()` / `ontbreekt()` / `waarschuwing()` / `exportMelding()` for the summary and the list before the export, `voegToe(finalDoc)` for the pages, `wis()` for "Alles wissen". A protected PDF is refused (pdf-lib cannot decrypt it). See `docs/armaturenboek.md` for storage. `controleer-suite.mjs` fails when a tool uses it without loading it or keeps its own `lichtplanDelen()`; `controleer-logica.mjs` checks the order in both tools.

## The projectenboek under 10 MB — `pdf-verkleinen.js`

A projectenboek with many fixture types and a lichtplan from DIALux easily runs past 10 MB, where mail servers start refusing it. Both tools pass the finished book through `PdfVerkleinen.tot(bytes, PDF_MAILGRENS_MB)` (10 MB, the user's limit, October 2026); below the limit nothing changes, so every ordinary book is byte-identical to before (the PDF regression stays green). Above it, **only images** are made lighter: measured, the baked presenters are largely vector work (the Sigma G2 IP44 sheet: 3.0 of its 3.4 MB are drawing operators, already Flate-compressed — recompressing them gains 1%), and deduplicating identical streams across presenters gains 0.1 MB, but the photos are 70–80% of the recent familiebladen and nearly all of a rendering-heavy lichtplan. Four steps, each starting from the originals, the first that gets under the limit wins: 2000 px / quality 0.85 for oversized JPEGs only; 1600 / 0.78 with flat (Flate) images over 300 kB going to JPEG; 1200 / 0.70 (flat over 100 kB); a last resort at 1000 / 0.60 in which small photos (from 12 kB) join too. Images are decoded in the browser (`createImageBitmap` for JPEG; `DecompressionStream('deflate')` plus `pngOntvoorspel()` for Flate with PNG predictors), redrawn on a canvas and swapped in as DCTDecode with the same dictionary otherwise, so an `/SMask` keeps working. Skipped because they would get worse: CMYK and other colour spaces than RGB/grey (ICCBased with N 3 or 1 counts), a `/Decode` that does something (`decodeNeutraal()` lets Ghostscript's `[0 1 …]` through), a colour-key mask, masks themselves, anything not 8 bits per component; a new version is only kept when it is at least 10% smaller. Measured: six of the heaviest presenters plus an 11.5 MB rendering lichtplan 24.0 → 10.0 MB in 8 s (the floor there is 7 MB of drawing work — the tool says so and suggests a link or fewer types); three types plus that lichtplan 20.6 → 9.8 MB in 3 s; the railtool's demo with it 16.6 → 5.8 MB. A real photo through all four steps is indistinguishable from the original at 3× zoom. The preview bar says "was 20,6 MB; de foto's zijn lichter gemaakt"; `controleer-logica.mjs` checks the predictors (all five) and the Decode rule.

**A lichtplan is made lighter as soon as it is loaded** (October 2026, at the user's request: "maak het lichtplan bij inladen lichter"), because the book was not the only thing it made heavy: "Project opslaan" carries every loaded lichtplan as base64 inside the project file — a third larger than the PDF — so an 11.5 MB DIALux export made a project file of over 15 MB that could not be mailed, and the browser's corner (about 5 MB) dropped it. `Lichtplan` now passes each chosen file through `PdfVerkleinen.licht(bytes, LICHTPLAN_MB)` before it goes into the state: the **first step always** (only JPEGs longer than 2000 px go to 2000 px — about 240 dpi over an A4, not visible), and the further steps **only while the file is still above 5 MB** (`LICHTPLAN_MB` in `lichtplan.js`: a book without a lichtplan is 3 to 6 MB, which leaves 5 for the plan). The stepping is one function, `verkleinInStappen()`, shared by `tot()` (the book: below the limit nothing at all) and `licht()` (the first step regardless), and `controleer-logica.mjs` checks its six cases with fake steps — the book below the limit untouched, the first step that gets under wins, otherwise the smallest; a lichtplan below the limit gets the first step only, also when that step changes nothing. Measured in the browser: the 11.5 MB rendering lichtplan → 0.7 MB in 1.6 s on the first step alone; a mixed one (a vector floor plan, a rendering at 1600 px and one at 3200 px) 0.58 → 0.33 MB, the 1600 px rendering untouched and the 3200 px one at 2000; twelve renderings already at 2000 px (6.0 MB, the first step does nothing) → 0.9 MB on the second; a plan without photos stays byte for byte what it was. With the heavy plan, the mixed one and a small one loaded, the project file is 1.4 MB and the book 4.2 MB. The message and the list say what happened ("11,5 MB → 0,7 MB (de foto's zijn lichter gemaakt)", "6 pagina's · 0,7 MB"), and the button reads "Lichtplan wordt ingeladen…" while it works. Choosing the same file twice is still caught: lightening gives the same bytes every time, and the raw bytes are compared too, for a plan that sits in an older project unlightened. A lichtplan in a project saved before this stays as it is until it is chosen again; a project file saved before 8 October does not load `pdf-verkleinen.js` at all, and then the plan goes in as it is (checked in the browser).

## Drawing layer — `pdf-huisstijl.js`

The drawing layer lives in **`pdf-huisstijl.js`** and is shared by all three PDF-producing tools (`index.html`, `armaturenboek.html`, and the vergelijker template). It used to be copy-pasted into each of them. Anything that has no knowledge of what goes on the page belongs here: the primitives, the house-style colours and fonts, and the fixed page furniture (cover, blue header band, grey diagonal footer, table layout). Composing the pages stays with each tool.

It is a plain `<script src="pdf-huisstijl.js">`, not an ES module — modules refuse to load over `file://`, which is how these tools are normally opened. The file is small and holds no image or font data, so loading it up front costs nothing; the heavy files (pdf-lib, `merk-data.js`, the presenters) still load on demand.

`PdfHuisstijl.tekenaar(doc, opt)` builds the layer for one document. The tool passes `haalY/zetY/haalPg/zetPg` so that `y` and `pg` stay its own variables — that is what lets the page code keep writing plain `y += 12` while `beginPage()` and `need()` move the write position. `opt.fonts` picks `'volledig'` (both heading fonts, for documents that carry the Pragmalux house style too) or `'distrilight'`; `opt.logos` and `opt.beelden` say which brand assets to embed. `omslag(project)` wants `project.datum` as ready-made text — the tools format dates differently.

`text()` takes `schuin:true` for an oblique letter — a sheared text matrix (12°), because no italic Open Sans is embedded; the width does not change, so `meet()` and the wrapping stay right. It is used for the quote on the armaturenboek's specialist card. All page content goes through `text/line/rect/circle/poly/dots`. They take **y from the top** of the page and convert to pdf-lib's bottom-left origin internally — keep that convention if you add primitives. `text()` uses real font metrics (`widthOfTextAtSize`) for centre/right alignment, and `pushOperators` for character squeeze (condensed caps) and letter spacing, which pdf-lib's `drawText` doesn't expose. Colours accept `'#RRGGBB'` or legacy `'r g b'` (0–1) strings via `col()`. Two wrap helpers exist and are not interchangeable: `wrapBreedte()` breaks on real text width, `wrapTekens()` on a character count.

**Tables** (`tableStart`/`tableRow`, used by the railtool's bill of materials and legend, both armaturenlijsten, the bandraster RFQ and the presenters) wrap each cell on spaces, and a single word wider than its column — a code like "Trappenhuizen/gangen(opbouw)" — is broken by `breekWoord()`: after `/` `-` `_` or before `(` where it can, mid-word only where it must, never leaving a first piece under three characters. It used to run straight through the next column. Every row has a 0.5 pt rule under it; a shaded row paints over the lower half of the rule above it, which on screen read as no rule at all, so a shaded row redraws that rule on top (not right under the header). A row passed with `{vervolg:true}` belongs to the one above (an accessory under its fixture): it takes that row's shade and does not advance the alternation. `controleer-logica.mjs` checks `breekWoord()` on the real code — its cutter also finds an indented declaration when there is no top-level one.

There is no test runner, so **before and after changing anything in this layer, run the regression check in `tools/`** — it makes each tool produce a PDF in a headless browser and compares them on content rather than bytes. See `tools/LEESMIJ-pdf-controle.md`.

Only the 14 standard PDF fonts are available; embedding a brand font needs `@pdf-lib/fontkit` vendored alongside pdf-lib. Raster logos (PNG/JPEG) work today via `doc.embedPng` / `embedJpg` — no extra dependency.

## Fixture types and their presenters — `armatuur-groepen.js`

A presenter belongs to a fixture **type**, not a variant: colour, wattage, light colour and dim protocol all share one presenter, and rows of the same type merge into a single chapter (`armaturenboek()` groups them). Types are `ARM_GROEPEN`; each has one presenter keyed by its id (`ag01`…`ag12`, plus `rail`).

**The table and the matcher live in `armatuur-groepen.js`**, loaded by both the railconfigurator and the armaturenboek. They used to be 253 duplicated lines in each file, kept in step by hand — and they had drifted: the lichtlijn groups existed only in the armaturenboek. The file declares `ARM_GROEPEN` and `matchArmGroep` as plain top-level names, exactly as the tools already used them, so no call site had to change. `tools/controleer-suite.mjs` fails if either HTML file grows its own copy again.

`matchArmGroep()` recognises the type from the free-text fixture name by token matching: it strips noise (colours, wattages, article codes — `ARM_STOPWOORDEN` / `ARM_GETAL` / `ARM_CODE`), then scores each group's name and `zoektermen`, requiring the distinctive first word and refusing ambiguous ties. So "Punto 15W zwart 3000K" resolves to Punto. Before tokenising, `armSchoon()` drops a "UGR<19" value and closes up an IP rating ("IP 65", "IP-65" → "IP65", as the sheets and type names write it), so a typed "Sigma IP 65" reaches the Sigma G2 IP65 (`ag82`) and not the plain Sigma, which is the IP44 (`ag34`). Measured over the 3,524 catalogue descriptions: no result changed, all 101 Sigma G2 articles get the sheet of their own rating (48 IP65, 53 IP44), and the 16 Sigma **G3** IP54 still get the G2 IP44 sheet for want of one of their own.

A Pragmalux description opens with the **fixture type** and only then names the product — "Pragmalux LED Downlight Mondial Opbouw IP54 …", "Plafonnière / Wandarmatuur Lumio-M …" — so `matchArmGroep()` first matches on the name behind that type word (`ARM_TYPEWOORDEN` → `armNaamZone()`) and falls back to the whole description only when that yields nothing. Without it the type word wins from the name: the Lumio came out as Wandarmatuur Qube IP65 (two hits, the type word plus IP65, against one for Lumio) and "Downlight Mondial Opbouw" as Downlight Mondial instead of Mondial Opbouw Pendel. Three details keep that from backfiring: the type word only counts **at the start** of the description (otherwise "Mondial Opbouw Pendel" would be cut at "Opbouw" and lose its own name), the name runs on until the specs begin — a colour, a number with a unit, an article code — with words that appear in some group name never ending it (that is what keeps the "Opbouw" in "Mondial Opbouw"), and a **distinctive** type word is scored along with the name, so "Pendelarmatuur Orion" still beats plain Orion and "Gevelarmatuur Squalo" still beats Squalo Mini. The generic ones (downlight, paneel, opbouw, spot) are `ARM_STOPWOORDEN` and stay out of the score. Words appearing in any group name are never stripped as noise (that's what keeps "GU10" alive). **Two rules sit on top of the score**, both found by checking whether every article of one catalogue family lands on the same presenter. First, **the kind at the start rules out a group of another kind** (`ARM_SOORT`, `armBeginSoorten()`, `ARM_GROEP_SOORT`): "LED Paneel 60x60cm Essence G2" came out as Downlight Essence G2, because G2 is in that group's search terms and not in the panel's, and "LED Paneel Clean" as Highbay Clean. Only kinds that really exclude each other count — not opbouw/inbouw (mounting: "Downlight Mondial Opbouw" is the Mondial Opbouw Pendel), not spot, plafonnière or wandarmatuur (the Lumio is both). **Paneel and bandraster are one kind** here, because the Flexcore presenter is titled "Paneel & bandraster Flexcore" and the Optic one lists bandraster sizes; **waterdicht is a kind of its own**, or a Highbay Essence became the Waterdicht Essence Classic G2 the moment the panel and downlight groups dropped out. Second, **a kind word alone points at nothing** — a name word has to hit as well: "Plafonnière / Wandarmatuur Polo" came out as Wandarmatuur Qube IP65 on the word "wandarmatuur" alone, and every nameless "LED Bandraster …" as Bandraster Miro. Measured over the whole catalogue (`controleer-logica.mjs` asserts it, with a lower bound that may only go up): 151 Pragmalux families land on one presenter, and the only three that split are real — the Sigma G2 against the Sigma G2 IP65, the Port M against the Port S, the Essence Classic G2 against the G3 IP66. Every family that lost its presenter in this change had a wrong one. **An IP rating is not a name either** (September 2026): "Plafonnière / Wandarmatuur Titandisc-M … IP65" became Wandarmatuur Qube IP65 on "wandarmatuur" and "ip65" alone, and so did the Soladisc, the Facio and the Parono; the Cyclone HT became Waterdicht Essence G3 IP66 on "waterdicht" and "ip66". The rating still adds to the score (it is what tells the Sigma G2 IP65 from the IP44), but it no longer counts as the name word a variant needs. Facio and Parono now get their own sheet, and the Soladisc and Cyclone HT none — better than the wrong one; the Titandisc got its own sheet in the same launch, with the Aludisc, the Eclipse and the Highbay Essence, and the Clean HACCP is rightly split in two (the G3 has its own sheet). The bound is 151 again, and four families split. **A group can require words** (`vereist`): the Soladisc IP65 sheet (`ag117`) is only for the Soladisc IP65 (Ø370, 2032491), not for the Soladisc-S/M/L, a different IP44 fixture with its own sheet (`ag118`, "Soladisc IP44") — without `vereist:['ip65']` the word "Soladisc" alone pointed at the IP65. A typed "Soladisc IP 65" finds the IP65 (the rating is closed up first), a bare "Soladisc" the IP44, the ordinary one; the catalogue family splits over the two, rightly, like the Sigma. The Cyclone HT IP66 has its own sheet too (`ag119`, "Waterdicht Cyclone"), and since October 2026 the Port-Nova IP65 (`ag120`, "Portiekarmatuur Port-Nova" — a different fixture from the Port-M and Port-S PKVW, which keep theirs; exactly its 13 catalogue articles moved, from no sheet to this one) and the Rondisc (`ag121`, its 6 articles; the Rondix panel, one letter apart, stays `ag33`), then the Opus (`ag122`, 31 articles) and the Verto 60 (`ag123`, 4) — exactly those 35 moved, from no sheet to their own. The Opus group is named plain "Opus" on purpose: as "Opbouwarmatuur Opus" the type word scored along and pulled the remote and the PIR sensor it shares with the Batten Lumea ("Batten Lumea IP44 /Opbouwarmatuur Opus …", 1099828 and 1099804) away from the Lumea, where they were. Bound 157, five families split. **A name that is not recognised may get a suggestion** (`armSuggestie()`, the "Bedoelde je Essence?" in the badge, which takes it over in one click in both the railtool and the armaturenboek). It is much stricter than the vergelijker's search suggestion, because here the product names the table does not know are simply in the input: at two edits, 87 of the catalogue's 733 unrecognised articles got a wrong type (Highbay Horizon → Orion, Straatverlichting Area → Arda, Rondisc → Rondix). So: only words from the name, at least five letters, same first letter, exactly one edit (a swapped pair of neighbours counts as one — `bewerkAfstand()` does that), exactly one table word at that distance, and the corrected name must actually be recognised. That gives zero suggestions on real articles, which the check asserts too; the price paid is that a four-letter typo ("Qbue", "Luan") gets none. `ARM_SERIES` lists the series that have several presenters where the name rarely says which is meant (the Mondial: ordinary, opbouw/pendel, PIR, nood, track; and the Ario: GU10 or with built-in LED — a description that names GU10 is the GU10, a full LED description the LED one, a bare "Ario" stays the GU10 as it always was); `armSerieKeuze(id)` gives the choices for a recognised type and `armKeuzeBlijft()` decides whether a choice survives a change of name — the armaturenboek uses both, see `docs/armaturenboek.md`. Each row also has a dropdown to override the detection explicitly, or set "Geen presenter"; `armGroepVan()` applies that precedence. `exportPdf()` warns (but still proceeds) about rows with a qty but no type, and about types whose presenter file is missing.

## Adding presenter PDFs

Presenters are large (~2 MB each), so they load **on demand at export time**, not at startup — `presenters/<id>.js` per presenter, listed in `window.PRESENTER_FILES` (`presenters-data.js`) so availability is known without downloading. `presenterData()` fetches via a dynamically injected `<script>` (works over `file://`, unlike `fetch`); `presenterAanwezig()` is the sync availability check. Inlining a blob directly in `window.PRESENTER_DATA` still works and takes precedence, but is loaded eagerly.

Don't hand-encode these. Drop the PDFs in `presenters-bron/` named by group id or name (`ag01.pdf`, `Punto.pdf`, `rail.pdf`) and run `node tools/maak-presenters.mjs`, which regenerates `presenters/` and `presenters-data.js`. That script rewrites the whole list from whatever is in `presenters-bron/`, so run it with **all** source PDFs present — with one file in the folder it leaves one id in `presenters-data.js` and the rest of the presenters fall out of the tool. It also cannot tell a blank export from a real presenter: `presenters/ag44.js` (Neo) was two pages without a single drawing operation — 42 MB of unreferenced resources — so it has been deleted and `ag44` is left out of `PRESENTER_FILES` by hand — with a note on its place — so the tool warns "presenter ontbreekt" instead of splicing in blank pages. Put it back once a working Neo familieblad is baked, and check a new presenter actually carries content before trusting it. Nor can it tell that a PDF is the wrong one: "Paneel SIGMA G2.pdf" was a byte-for-byte copy of the IP65 sheet, so every Sigma G2 IP44 got the IP65 presenter until the real IP44 familieblad replaced it (September 2026, now `'Paneel Sigma G2 IP44'` in `GROEPEN`, so an old "Paneel SIGMA G2.pdf" left in `presenters-bron/` is skipped rather than baked over it). `controleer-presenters.mjs` now reports two presenters with identical content; the one known pair, Orion (`ag07`) being a copy of the Arda sheet (`ag06`), is listed in its `BEKEND_DUBBEL` until the real Orion sheet arrives. To bake a single presenter without the rest of `presenters-bron/`, run the script in a scratch copy and take over only `presenters/<id>.js`. That script is a data-prep utility, not a build step — the app still runs by opening `index.html` directly. `presenters-bron/` is gitignored; the generated `presenters/*.js` is committed. Keep the `GROEPEN` table in that script in sync with `ARM_GROEPEN`.

**A fixture without a Pragmalux familieblad** can get one made in the same style: `tools/familiebladen/familieblad.html?blad=<naam>` draws a two-page sheet from `tools/familiebladen/<naam>.js` with the drawing layer in the Pragmalux theme — the navy header with the wordmark and the name in two weights, a key-figures band, KENMERKEN, then PRODUCTGEGEVENS (labels in a navy column), the row of round feature badges, AFMETINGEN, BESTELGEGEVENS and the standard Pragmalux footer line, all measured off the Port-Nova sheet. Open it from disk, press "PDF opslaan" and bake it like any other sheet. The data file holds only what a source states. The first was the Rondisc (`ag121`, October 2026), from the product card the user supplied and the catalogue descriptions; when the real familieblad arrived the same week it replaced the baked sheet and `rondisc.js` went (it is in the git history as an example of the format). Worth knowing: the real sheet differs from that product card on two figures — beam 112° against ">80°", lifetime 173,000 h (L80B10) against ">100.000" — so a product card is a stopgap, not a source to trust over the familieblad.

Presenter PDFs are typically 0.5–4+ MB each of high-resolution product photography, and `assembleFinalPdf()` always includes `rail` + `achterpaginas` plus one presenter per used fixture type — a project with several types can easily push the downloaded PDF past a mailable size (measured in the armaturenboek: 3.0 MB for one type, 4.4 for three, 5.8 for six). Both PDF tools now say how big the file turned out — in the preview bar — and above `PDF_MAILGRENS_MB` (10 MB since October 2026; it was 8) they first make the photos in the book lighter (`pdf-verkleinen.js`, above); `meldPdfGrootte()` only warns when the book is still over the limit after that. Compressing the source PDFs below still pays: it keeps every book lighter from the start. `pdf-lib` can't downsample images already embedded in a copied page, so any size reduction has to happen on the source PDF before baking. Run `node tools/comprimeer-presenters.mjs` (needs Ghostscript on PATH — `winget install --id ArtifexSoftware.Ghostscript -e` or `choco install ghostscript`) before `maak-presenters.mjs` when adding or replacing a presenter; it recompresses images in `presenters-bron/*.pdf` in place (keeping a pristine copy in `presenters-bron/origineel/`) and reports the size saved per file. The sheets are English, so "Zena Round"/"Zena Square" point there too, and a bare "Zena" (or "Zena 2V") is the round one, as "Ario" is the GU10 — without that search term the longest name, Vierkant 2V, won; the label offers the four as a series (`ARM_SERIES`). Measured over every lookup source: exactly 17 articles move, from no sheet to their own — the 14 on the sheets plus the three "met bladveren" versions (B4608082, B4608099, B4608211), which are not on any sheet but are called Zena Rond.
