# Armaturenboek — `armaturenboek.html`

> Part of the Distrilight tools suite — start from `CLAUDE.md` in the repo root, which
> holds the hard rules, the map of the repo and how to check a change. This file is
> the depth for one tool: read it before you change `armaturenboek.html`.

`armaturenboek.html` is the **Armaturenboek** tool: pick the fixtures for a project and it composes the book — cover, an Armaturen chapter page, the armaturenlijst table, and one externally-supplied Pragmalux presenter per recognised type, spliced in by `assembleArmaturenboekPdf()`. The armaturenlijst is optional (`st.toonLijst`, the "Armaturenlijst in de PDF" tick in the Armaturen block): a book that goes out as product documentation alone does not always want the overview table. Only that one page drops — the chapter page and the presenters stay, and `bookGroups` is filled outside the `if`, so the stamps and the splicing don't notice. The "presenter ontbreekt" line at the foot of that table goes with it; the on-screen warning is what remains. **The table follows the order of the rows in the tool**, not the grouping by type: someone who types the rows in the order of the bestek wants to read them back that way, and grouping made a recognised type jump up to its own kind while the unrecognised rows sank to the bottom. The presenters behind it follow the same order by themselves — `armaturenboek()` puts each type where it first occurs. The ↑/↓ buttons at the head of each row move a row, and swap the **contents** of the two slots rather than the slots themselves, so `arm01..armNN` stay in order and the labels, the save and the restore (which sorts on slot number) need to know nothing about it. An uploaded presenter hangs on the slot (`sp<armId>`), so `wisselArmRijen()` moves that with it by hand. Unlike `index.html` that splicing needs no page-index bookkeeping: every own page is copied first, then the presenters are appended, so inserting a page changes nothing else.

**The row, the stamp and the list are shared with the railtool** through `armatuur-rij.js` (`armRijDelen()`, `stempelPresenter()`, `armLijstKolommen()`, `armBoekGroepen()`, `armWisselRijen()` — see `docs/gedeeld.md`), so the railtool's armaturenboek works the same way; the paragraphs below describe that shared behaviour, and the function names in them now live in that file (`typeOnbekend()` is `armTypeOnbekend()`, `verzamelSpecialPresenters()` calls `armEigenPresenters()`, `paintBadge()` is part of `armRijDelen()`). A fixture whose type `matchArmGroep()` cannot place gets an **upload button on its own row**, whatever is in the article-code field — an article code is no reason to leave a row without a presenter. `armGroepVan()` therefore checks for an uploaded PDF (`sp<armId>`) on every row before anything else: uploading is a deliberate act and wins over name recognition, and the × next to the button undoes it. The button is decided by `typeOnbekend()`, which deliberately ignores the uploaded PDF — otherwise it would disappear the moment you used it and the upload could not be replaced. `"special"` in the article-code field still forces the button on a row that has no name yet, and `verzamelSpecialPresenters()` collects `sp<armId>` for **every** row rather than only the special ones, so an upload survives "Project opslaan".

**A series with more than one presenter gets a choice in the label.** "Mondial" usually means the ordinary downlight (ag21), but sometimes the surface-mounted or pendant version — which share one presenter, ag25 "Mondial Opbouw/Pendel" — or the PIR, emergency or track version, and the name inside sales types rarely says which. So when the recognised type belongs to a series in `ARM_SERIES` (`armatuur-groepen.js`), `paintBadge()` turns the green label into a `<select>` with that series' presenters, the recognised one preselected. A different choice goes into `s.groep` — the field `armGroepVan()` already reads as a manual override, so it is saved with the project and moves with ↑/↓ without further code; choosing the recognised one again empties it. `armKeuzeBlijft()` drops a series choice when the name changes to something that points at a different type by itself ("Punto", or "Mondial PIR"), but keeps it when only the wattage or colour changes. A choice outside a series is never dropped. The badge's own Enter/Space handler (for the typo suggestion) only reacts on the badge itself, so the keys still work inside the select.

The **code stamp comes in two styles**, chosen per fixture row and stored as `s.stempel` (`STEMPELSTIJLEN`, `stempelZwart()`): `'wit'` puts it in the presenter's dark header band in the group's own colour — white, or the group's `stempelKleur` where the header is light, as on the Dio — and `'zwart'` puts it in black and a little higher, for a page whose header is light or whose layout is unknown. Both baselines were judged on the print: measured at 27 and 47, then the white one moved 3 mm down and the black one 7 mm up, which is where the 35.5 and 27.2 in `stempelCode()` come from. **White is the default, except on a special** (a row with its own uploaded PDF): those usually come out of the DLC tool, whose sheet has only a thin black band (to y 23.7) with the slanted logo block hanging off it on the right (left edge x 444.8 at y 24 to 468.3 at y 57.4). On the Pragmalux spot a white stamp landed on white paper under that band and was invisible, and a black one ran its last letter into the logo block, 4 pt under the band. So a special gets its own spot, `STEMPEL_SPECIAL`, in either colour: right-aligned on x 435.85 — the DLC grid line where the gutter between detail 4 and 5 starts, 9 pt before the corner of the logo block and 17 pt from it at letter height — with the capitals one gutter (12 pt) under the band; three codes still end above the title. A special defaults to black (`stempelZwart(s, special)`: an explicit choice wins, otherwise black on a special and white elsewhere); white stays available for an own PDF with a tall dark header. `controleer-logica.mjs` checks the spot against the measured band and logo block for one to three codes, and that the old spot failed it. The toggle only appears on a row that will actually be stamped (it has a presenter and a code). One presenter page carries one stamp, so when several rows share a group, one asking for black makes it black — you only ask for that because the page's header is light, which is a property of the page.

The panel blocks run **fixtures first, then the project data, then the briefing** — the fixture rows are the work, the briefing fields are filled in once per project — and that last block is a `<details>` that starts closed, with the chosen variant and the number of empty fields in its summary line so you can read the state without opening it.

Under 980px the summary panel drops below the form and takes the export buttons with it, so a fixed bar (`.cfg-balk`, in `armaturenboek.html` and `index.html`) keeps them in reach. Its buttons carry `data-spiegel="<id>"` and do nothing themselves: they click the real button in the panel, and mirror its `disabled` state and label through a MutationObserver — one place where the action lives, and the bar still says "Bezig…" while a PDF is being made.

**Soort opdracht** decides the wording of the **briefing page "Introductie"**, which sits directly behind the cover in both cases. `st.soort` is `'lichtberekening'` (the default) or `'vergelijking'`; `briefInhoud()` returns that variant's text as a list of blocks, and one renderer draws it. The lichtberekening promises a light design against NEN-EN 12464-1:2021 and carries no disclaimer; the vergelijking is shorter and ends in one disclaimer paragraph. **The texts are the thing that gets edited** — they are plain strings in `briefInhoud()`, deliberately kept out of the drawing code.

The page is a redrawing of the supplied design (`docs/ontwerp/AB Briefing vergelijking.pdf`, with the Word original beside it): the measurements in the `BRIEF` table were read out of that document rather than eyeballed. Every gap in `BRIEF.gaten` is the distance to the **top of the previous line**, which is how they were measured, so a block only has to name which gap precedes it.

Three document fields feed the text, declared once in `BRIEF_VELDEN` (id, label, fallback placeholder, and which variants use it): **Bestek** (both variants), **Technische tekeningen** (lichtberekening) and **Armaturenboek** (the vergelijking's disclaimer). That one table drives the panel fields, the state keys, the "not filled in" warning and the placeholders, so adding a fourth field is one entry plus a reference in the text. Each field takes one name per line and renders them as an enumeration ("a", "a en b", "a, b en c"); with more than one name "het document" becomes "de documenten" and "de tekening" "de tekeningen", otherwise the sentence does not run. All three fields are always shown — the ones the current variant does not use are marked and dimmed rather than hidden, so you can fill everything in and switch variant without losing anything. The project name comes from the field that was already there. Empty fields fall back to the design's own `[projectnaam]` / `[Bestek]` / `[Technische tekening]` / `[Armaturenboek]` placeholders, and both the panel and the pre-export alert warn when that is about to happen. The grey quote block grows if the document list needs more room.

The panel fields are built from `BRIEF_VELDEN` at startup, so the container is emptied first: "Project opslaan" bakes the DOM as it stands, and a saved project already contains them. Without that, reopening would append a second, empty set — and `getElementById` would find the empty one.

**Below the briefing text come the contact persons.** Three selects in the briefing block pick the **projectuitwerker**, the **accountmanager** and the **commerciële binnendienst** (`st.projectuitwerker` / `st.accountmanager` / `st.binnendienst`, ids from `medewerkers.js`); the page then gets a "Contactgegevens" block with the chosen people side by side — name, function in blue, direct and general number, mobile where the source has one, e-mail — and a person who is not chosen leaves no empty column. A projectuitwerker with a personal note (`noot`) also gets **"Onze specialist"**: the blue card from the supplied contact sheets ("Contactgegevens - Update sep 2026.pdf") with photo, name and function in Poppins, the note in an oblique Open Sans and T/E. Olivia and Julia have no note or photo yet, so for them it is the contact block only; the select says which is which ("Met blauw vlak" / "Alleen contactgegevens"). The measurements, the three selects (`contactKeuze()`) and the drawing (`tekenContactpersonen()`) live in `contactpersonen.js`, shared with the railtool, which puts the same block on an introduction page of its own — see `docs/gedeeld.md`. Every measurement is in `CONTACT`, read off those contact sheets and off the example page the user supplied; the card never breaks across pages, and when it misses by a little — the vergelijking's disclaimer makes the text longer — the gaps above it tighten (`specialistGatKrap`) before it moves to the next page, rather than leaving a card alone on an otherwise empty page. Karlijn's photo arrives already cut round on a blue square in a slightly different blue (#117ABE against the card's #0E7DC2), so it is clipped round a little inside that edge (`rond:true`) instead of showing a square. The data is `medewerkers.js` (hand-kept: add a colleague there) and the photos `medewerker-fotos.js`, generated by `node tools/maak-medewerker-fotos.mjs` from `docs/bronnen/medewerkers/<id>.jpg`; `controleer-logica.mjs` checks both against each other. **The repo is public, so all of this — photos, notes, direct and mobile numbers — is on GitHub and the website; the user agreed to that in September 2026.** A saved project keeps the chosen ids; an id that has since left `medewerkers.js` counts as not chosen. The "Briefing" heading is Poppins now too, as in the design (it was Open Sans), so the three headings on the page match.

Three things about that page are worth knowing before changing it. `rijkeRegels()`/`tekenRegel()` are a small rich-text wrapper — words carry a bold flag and a word that follows without a space (the full stop after a bold project name) stays glued to it, so wrapping happens on real text width across the bold boundaries. The bullet is drawn as a circle, not typed: `pdfTxt()` does not know `•` and would render a question mark. And the page title goes through `paginaKop()`, which upper-cases — so it reads `INTRODUCTIE`, matching `ARMATURENLIJST` elsewhere in the same book rather than the supplied document's title case.

Before a family is picked, the preview is an empty PDF frame — a near-full-screen dark grey rectangle that reads as a fault — so `#bladleeg` lies over it with what the tool is about and the four steps; `ververs()` hides it as soon as there is something to show. The railconfigurator's step 1 carries the same kind of note (`.c2-uitleg`), because that step is one choice on an otherwise empty screen.
