# Armaturenboek — `armaturenboek.html`

> Part of the Distrilight tools suite — start from `CLAUDE.md` in the repo root, which
> holds the hard rules, the map of the repo and how to check a change. This file is
> the depth for one tool: read it before you change `armaturenboek.html`.

`armaturenboek.html` is the **Armaturenboek** tool: pick the fixtures for a project and it composes the book — cover, an Armaturen chapter page, the armaturenlijst table, and one externally-supplied Pragmalux presenter per recognised type, spliced in by `assembleArmaturenboekPdf()`. The armaturenlijst is optional (`st.toonLijst`, the "Armaturenlijst in de PDF" tick in the Armaturen block): a book that goes out as product documentation alone does not always want the overview table. Only that one page drops — the chapter page and the presenters stay, and `bookGroups` is filled outside the `if`, so the stamps and the splicing don't notice. The "presenter ontbreekt" line at the foot of that table goes with it; the on-screen warning is what remains. **The table follows the order of the rows in the tool**, not the grouping by type: someone who types the rows in the order of the bestek wants to read them back that way, and grouping made a recognised type jump up to its own kind while the unrecognised rows sank to the bottom. The presenters behind it follow the same order by themselves — `armaturenboek()` puts each type where it first occurs. The ↑/↓ buttons at the head of each row move a row, and swap the **contents** of the two slots rather than the slots themselves, so `arm01..armNN` stay in order and the labels, the save and the restore (which sorts on slot number) need to know nothing about it. An uploaded presenter hangs on the slot (`sp<armId>`), so `wisselArmRijen()` moves that with it by hand. There is no upper limit to the rows: 12 are ready and `zorgVoorLegeSlot()` adds an empty one as soon as the last is filled (the railtool now does the same). `herstelProject()` merges the saved rows onto 12 **empty** ones, not onto what is on screen: a row typed before clicking "Verder waar je gebleven was" (arm13) that the saved project does not have used to stay in the restored project (measured). Unlike `index.html` that splicing needs no page-index bookkeeping: every own page is copied first, then the presenters are appended, so inserting a page changes nothing else.

**The row, the stamp and the list are shared with the railtool** through `armatuur-rij.js` (`armRijDelen()`, `stempelPresenter()`, `armLijstKolommen()`, `armBoekGroepen()`, `armWisselRijen()` — see `docs/gedeeld.md`), so the railtool's armaturenboek works the same way; the paragraphs below describe that shared behaviour, and the function names in them now live in that file (`typeOnbekend()` is `armTypeOnbekend()`, `verzamelSpecialPresenters()` calls `armEigenPresenters()`, `paintBadge()` is part of `armRijDelen()`). A fixture whose type `matchArmGroep()` cannot place gets an **upload button on its own row**, whatever is in the article-code field — an article code is no reason to leave a row without a presenter. `armGroepVan()` therefore checks for an uploaded PDF (`sp<armId>`) on every row before anything else: uploading is a deliberate act and wins over name recognition, and the × next to the button undoes it. The button is decided by `typeOnbekend()`, which deliberately ignores the uploaded PDF — otherwise it would disappear the moment you used it and the upload could not be replaced. `"special"` in the article-code field still forces the button on a row that has no name yet, and `verzamelSpecialPresenters()` collects `sp<armId>` for **every** row rather than only the special ones, so an upload survives "Project opslaan".

**A series with more than one presenter gets a choice in the label.** "Mondial" usually means the ordinary downlight (ag21), but sometimes the surface-mounted or pendant version — which share one presenter, ag25 "Mondial Opbouw/Pendel" — or the PIR, emergency or track version, and the name inside sales types rarely says which. The Ario is such a series too since September 2026: with a GU10 fitting (ag09) or with built-in LED (ag113), each with its own sheet. So when the recognised type belongs to a series in `ARM_SERIES` (`armatuur-groepen.js`), `paintBadge()` turns the green label into a `<select>` with that series' presenters, the recognised one preselected. A different choice goes into `s.groep` — the field `armGroepVan()` already reads as a manual override, so it is saved with the project and moves with ↑/↓ without further code; choosing the recognised one again empties it. `armKeuzeBlijft()` drops a series choice when the name changes to something that points at a different type by itself ("Punto", or "Mondial PIR"), but keeps it when only the wattage or colour changes. A choice outside a series is never dropped. The badge's own Enter/Space handler (for the typo suggestion) only reacts on the badge itself, so the keys still work inside the select.

The **code stamp comes in two styles**, chosen per fixture row and stored as `s.stempel` (`STEMPELSTIJLEN`, `stempelZwart()`): `'wit'` puts it in the presenter's dark header band in the group's own colour — white, or the group's `stempelKleur` where the header is light, as on the Dio — and `'zwart'` puts it in black and a little higher, for a page whose header is light or whose layout is unknown. Both baselines were judged on the print: measured at 27 and 47, then the white one moved 3 mm down and the black one 7 mm up, which is where the 35.5 and 27.2 in `stempelCode()` come from. **White is the default, except on a special** (a row with its own uploaded PDF): those usually come out of the DLC tool, whose sheet has only a thin black band (to y 23.7) with the slanted logo block hanging off it on the right (left edge x 444.8 at y 24 to 468.3 at y 57.4). On the Pragmalux spot a white stamp landed on white paper under that band and was invisible, and a black one ran its last letter into the logo block, 4 pt under the band. So a special gets its own spot, `STEMPEL_SPECIAL`, in either colour: right-aligned on x 435.85 — the DLC grid line where the gutter between detail 4 and 5 starts, 9 pt before the corner of the logo block and 17 pt from it at letter height — with the capitals one gutter (12 pt) under the band; three codes still end above the title. A special defaults to black (`stempelZwart(s, special)`: an explicit choice wins, otherwise black on a special and white elsewhere); white stays available for an own PDF with a tall dark header. `controleer-logica.mjs` checks the spot against the measured band and logo block for one to three codes, and that the old spot failed it. The toggle only appears on a row that will actually be stamped (it has a presenter and a code). One presenter page carries one stamp, so when several rows share a group, one asking for black makes it black — you only ask for that because the page's header is light, which is a property of the page.

**Accessories.** Some fixtures come with a separate article — the surface-mounting set with a Mondial Opbouw, a pendant set — that has its own article code and name but belongs to the fixture's CODE and gets no presenter. The "+ Accessoire" button at the end of a row adds a sub-row under it (article code, name, an optional quantity); × takes it away again. In the armaturenlijst an accessory sits directly under its fixture, with the Code cell empty and the fixture's shade, so the two read as one entry (H1 — the Mondial, then its set). It changes nothing else: the presenters, the stamps and the warnings look at the fixture only. `armAccessoireDelen()`, `armAccessoires()` and the `regels` of `armLijstKolommen()` in `armatuur-rij.js` (see `docs/gedeeld.md`); `controleer-logica.mjs` holds the rules. The quantity and the button sit together at the end of the row (`.c2-armstaart`), so on a narrow screen they wrap as one, to the right, still above the accessories' quantity and ×. The railtool has the same button (`docs/railtool.md`).

**Totaal projectboek.** The block after the briefing takes the lichtplan as a PDF (the DIALux or AutoCAD output the user already has) and puts it in the book **directly after the introduction**, behind the chapter page "Lichtberekening": cover, introductie, Lichtberekening, the lichtplan's own pages as they are (landscape stays landscape), then the Armaturen chapter, the armaturenlijst, the presenters and the achterpagina's. `boekDelen()` holds that order as data (the lichtplan part is `lichtplanDelen()` from `lichtplan.js`) and `assembleArmaturenboekPdf()` walks it; `buildArmaturenboekPdf()` reports `naIntroductie`, the number of its own pages up to and including the introduction. No page carries a number, so inserting pages shifts nothing. The chapter page is the supplied design (`AB_Lichtberekening.pdf`) baked like the achterpagina's, as `presenters/lichtberekening.js` (`'lichtberekening'` in `GROEPEN` of `maak-presenters.mjs`, compressed 0.47 → 0.10 MB with no visible difference) and inserted without a stamp. The block and the handling live in **`lichtplan.js`, shared with the railtool** (`Lichtplan.koppel()`, `lichtplanDelen()`), so both tools do it the same way. `st.lichtplan` holds only `{naam, paginas}`; the PDF itself is `Lichtplan.pdf` and goes into "Project opslaan" as `payload.lichtplan`, like uploaded presenters. The browser's corner (`project-opslag.js`) tries the whole project first but holds about 5 MB, and a lichtplan easily runs larger; then the light version is kept, without the PDF. A project resumed from there knows the name but not the file: the block, the summary and the export say it has to be chosen again, and the book goes out without it rather than failing (measured with a 12 MB lichtplan; a small one simply comes back). A protected PDF is refused on loading — pdf-lib cannot decrypt, and its pages would come out blank or mangled. `controleer-logica.mjs` checks the order in `boekDelen()`.

The panel blocks run **fixtures first, then the project data, then the briefing** — the fixture rows are the work, the briefing fields are filled in once per project — and that last block is a `<details>` that starts closed, with the chosen variant and the number of empty fields in its summary line so you can read the state without opening it.

Under 980px the summary panel drops below the form and takes the export buttons with it, so a fixed bar (`.cfg-balk`, in `armaturenboek.html` and `index.html`) keeps them in reach. Its buttons carry `data-spiegel="<id>"` and do nothing themselves: they click the real button in the panel, and mirror its `disabled` state and label through a MutationObserver — one place where the action lives, and the bar still says "Bezig…" while a PDF is being made.

**Soort opdracht** decides the wording of the **briefing page "Introductie"**, which sits directly behind the cover in both cases. `st.soort` is `'lichtberekening'` (the default) or `'vergelijking'`; `briefInhoud()` returns that variant's text as a list of blocks, and one renderer draws it. The lichtberekening promises a light design against NEN-EN 12464-1:2021 and carries no disclaimer; the vergelijking is shorter and ends in one disclaimer paragraph. Which sentences appear depends on the sources filled in (below). **The texts are the thing that gets edited** — they are plain strings in `briefInhoud()`, deliberately kept out of the drawing code. All of the page — measurements, text, the panel block and the drawing — is in **`briefing.js`**, shared with the railtool, which puts exactly the same page in its PDF (see `docs/gedeeld.md`).

The page is a redrawing of the supplied design (`docs/ontwerp/AB Briefing vergelijking.pdf`, with the Word original beside it): the measurements in the `BRIEF` table were read out of that document rather than eyeballed. Every gap in `BRIEF.gaten` is the distance to the **top of the previous line**, which is how they were measured, so a block only has to name which gap precedes it.

**Four sources feed the text, and all four are optional**: **Bestek**, **Technische tekeningen**, **Armaturenboek** and **E-mail** (its subject), declared once in `BRIEF_VELDEN` (id, label, how the source is named in running text with one name and with more — `ev`/`mv` — and whether the names go between quotes). Only what is filled in appears on the page, and the sentences follow from what there is; you choose a source by typing a name in it. It used to be three fields per variant with the design's placeholders as fallback, so a vergelijking without a bestek still printed "[Bestek]" — the user asked for this (October 2026). The roles: in a **lichtberekening** the drawing is the basis ("Op basis van de tekening: **…** ontwikkelen wij …", or "Wij ontwikkelen …" without one) and bestek, armaturenboek and e-mail are the uitgangspunten ("… uitgewerkt volgens de uitgangspunten zoals omschreven in …", or only the norm sentence without any); in a **vergelijking** all sources together are the basis of the proposition and of the disclaimer, and the armaturenboek is what the fixtures may deviate from ("de gevraagde armaturen" without one). `briefGroepen()` merges sources that share a noun — bestek and armaturenboek are both "het document", because their names already say what they are ("Bestek E-installaties …") — so two of them become "de documenten **X en Y**"; `briefBronnen()` writes the list ("het document **X** en de e-mail met als onderwerp **“Y”**"), `briefVraagSlot()` the closing sentence of "De vraag": with one kind of source exactly as in the design ("… vastgelegd in het document:" and the name in bold on the line below), with more kinds the whole list on that line, with none no closing sentence. Each field still takes one name per line, rendered as an enumeration. Only the project name keeps a placeholder (`[projectnaam]`), and only that is warned about. The summary line of the closed block names the sources that will appear. `controleer-logica.mjs` checks the combinations (e-mail only, bestek and drawings as in the design, bestek + armaturenboek, mixed kinds, none). The grey quote block grows if the list needs more room.

The panel fields are built from `BRIEF_VELDEN` at startup by `briefingKeuze()`, so the container is emptied first: "Project opslaan" bakes the DOM as it stands, and a saved project already contains them. Without that, reopening would append a second, empty set — and `getElementById` would find the empty one.

**Below the briefing text come the contact persons.** Three selects in the briefing block pick the **projectuitwerker**, the **accountmanager** and the **commerciële binnendienst** (`st.projectuitwerker` / `st.accountmanager` / `st.binnendienst`, ids from `medewerkers.js`); the page then gets a "Contactgegevens" block with the chosen people side by side — name, function in blue, direct and general number, mobile where the source has one, e-mail — and a person who is not chosen leaves no empty column. A projectuitwerker with a personal note (`noot`) also gets **"Onze specialist"**: the blue card from the supplied contact sheets ("Contactgegevens - Update sep 2026.pdf") with photo, name and function in Poppins, the note in an oblique Open Sans and T/E. Olivia has no note or photo yet, so for her it is the contact block only (Julia got her card in October 2026); the select says which is which ("Met blauw vlak" / "Alleen contactgegevens"). The measurements, the three selects (`contactKeuze()`) and the drawing (`tekenContactpersonen()`) live in `contactpersonen.js`, shared with the railtool, which puts the same block on an introduction page of its own — see `docs/gedeeld.md`. Every measurement is in `CONTACT`, read off those contact sheets and off the example page the user supplied; the card never breaks across pages, and when it misses by a little — the vergelijking's disclaimer makes the text longer — the gaps above it tighten (`specialistGatKrap`) before it moves to the next page, rather than leaving a card alone on an otherwise empty page. Karlijn's photo arrives already cut round on a blue square in a slightly different blue, so it is clipped round a little inside that edge (`rond:true`) instead of showing a square. **The new profile photos (October 2026)** come in that same shape, 2000×2000 pixels and 260 kB each — far too big for a file every tool loads at startup and every PDF with the card carries. `node tools/maak-pasfoto.mjs <foto> <id>` finds the circle (the first non-blue pixel from each edge), crops to the square around it and reduces it to 400×400 (about 20 kB) into `docs/bronnen/medewerkers/<id>.jpg`; then `node tools/maak-medewerker-fotos.mjs` as before, and `rond:true` on that colleague in `medewerkers.js`. Karlijn's is the first (October 2026); the others follow as the photos come in. The data is `medewerkers.js` (hand-kept: add a colleague there) and the photos `medewerker-fotos.js`, generated by `node tools/maak-medewerker-fotos.mjs` from `docs/bronnen/medewerkers/<id>.jpg`; `controleer-logica.mjs` checks both against each other. **The repo is public, so all of this — photos, notes, direct and mobile numbers — is on GitHub and the website; the user agreed to that in September 2026.** A saved project keeps the chosen ids; an id that has since left `medewerkers.js` counts as not chosen. The "Briefing" heading is Poppins now too, as in the design (it was Open Sans), so the three headings on the page match.

Three things about that page are worth knowing before changing it. `rijkeRegels()`/`tekenRegel()` are a small rich-text wrapper — words carry a bold flag and a word that follows without a space (the full stop after a bold project name) stays glued to it, so wrapping happens on real text width across the bold boundaries. The bullet is drawn as a circle, not typed: `pdfTxt()` does not know `•` and would render a question mark. And the page title goes through `paginaKop()`, which upper-cases — so it reads `INTRODUCTIE`, matching `ARMATURENLIJST` elsewhere in the same book rather than the supplied document's title case.

Before a family is picked, the preview is an empty PDF frame — a near-full-screen dark grey rectangle that reads as a fault — so `#bladleeg` lies over it with what the tool is about and the four steps; `ververs()` hides it as soon as there is something to show. The railconfigurator's step 1 carries the same kind of note (`.c2-uitleg`), because that step is one choice on an otherwise empty screen.
