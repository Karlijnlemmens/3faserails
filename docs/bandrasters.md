# Bandrasters — `bandrasters.html`

> Part of the Distrilight tools suite — start from `CLAUDE.md` in the repo root, which
> holds the hard rules, the map of the repo and how to check a change. This file is
> the depth for one tool: read it before you change `bandrasters.html`.

`bandrasters.html` is the **Bandrasters** tool: a per-position intake for bandraster (grid-ceiling) replacement projects — the existing fixture on the left, the Distrilight alternative on the right — that yields two deliverables, a **technical product sheet** for the customer and an **RFQ list** for the manufacturer who has to build the alternatives.

It replaces `Bandraster_Intake_Nieuw_V3.xlsx`. Everything that lived on that workbook's hidden `Datasheet` sheet (the dropdown lists, the lumen table per TL tube × CRI/colour temperature, the optic efficiencies) is now the data tables at the top of the script; the `Formulier` formulas are the calculation layer, and the English `Bestelformulier` columns are the RFQ. The workbook had three fixed intake sheets; here the number of positions is free. Three things deliberately differ from it, each with a comment saying why: **5000K is not offered** (the lumen table only has columns for 2700/3000/4000/6500K per CRI, so 5000K always ran into "Gegevens Ontbreken"); the control/connector dependency is keyed on an explicit `groep` field rather than on the spelling of the control name (the workbook's list said `Aan-uit` while its formulas tested `Aan-Uit`, leaving the connector list empty for two of the five controls); and the RFQ carries the **alternative's** housing colour, where `Bestelformulier!P21` pointed at the existing fixture's.

The calculation is the workbook's, verified against its worked example (project 7633: 1× TL5-35W behind Prisma at 4000K/80+ → 2230 lm existing, 16 W and 2130 lm for a microprismatic alternative): existing lumen = tubes × lumen(tube, CRI+colour temp) × old optic efficiency; then wattage = `floor(lm / new optic efficiency / efficacy)` capped at a maximum, and new lumen = W × efficacy × new optic efficiency. Efficacy (140 lm/W) and the cap (60 W) live in `P.instellingen` rather than as constants, so the tool can move with a better LED generation without a code change — but they are **no longer shown**: neither as fields in the project card nor as a Systeemrendement row on the product sheet. Bringing them back is two inputs bound to `P.instellingen` (see the note in `bindProject`).

**Under 640px the intake folds**: existing | field name | alternative does not fit side by side, so the field name moves above the left box (`data-veld` on both cells, set in `tekenIntake()`, shown through `::before`; invisible on the right so both boxes start at the same height) and the two boxes keep half the width each. The single-column werkblad below 1180px is `minmax(0,1fr)`, not `1fr` — a `1fr` column is never narrower than its widest content, and the intake stretched the whole page to 606px on a 390px phone. Nothing changes on a laptop. The right-hand column mirrors the left until you overrule a field — `volgt[id] === false` marks it loose, `rechts()` is the single place that resolves which value applies, and a `↺` button re-couples it. A connector that does not exist in the list belonging to the chosen control counts as *not filled in* rather than being silently cleared, so it cannot slip into the RFQ after a control change or after reopening an older project.

The **product sheet** carries the **DLC** house style (same `M` measurement table as `dlc.html`, same baseline convention) but with field groups of its own — Algemeen, Afmetingen, Lichttechniek, Elektrisch. Empty fields and empty groups drop out, as in `dlc.html`. It is a sheet about the product, not about the job: what the alternative replaces and which project it is for stay in the tool and in the RFQ. Artikelcode falls back to **Special** when no product code is filled in, since a bandraster alternative is a one-off. The position's own **Bestekcode** — a field at the top of the intake card, next to the position description, not a row in the grid — is stamped into the header band, at the armaturenboek's stamp geometry (27 pt down, 11 pt, right-aligned, extra codes stacked 13 pt apart, shrinking rather than shifting when too wide) — with two deliberate differences, both forced by the artwork: it ends 155 pt from the right edge instead of 145.4, because the diagonal edge of the band's white wedge sits at x=445..453 at that height, and it is drawn in the sheet's ink rather than white, because it lands on that white wedge. `M.stempel` holds those numbers; a `;` in the field splits it into several stamped lines. At the foot of the sheet it repeats the alternative's optic and connector photo, side by side with a hairline and caption in the table's own style — no heading above them; the captions say what they are. The block is pinned above the footer line rather than following the table, so a short sheet does not leave it floating in the middle; when the table runs into that area the block moves to a new page (`M.foto`, at the end of `bouwProductblad`). It draws with the shared layer's own `sluitBeeldIn`/`beeldPassend`, so a photo pasted in as PNG works alongside the generated JPEGs. Instead of a photo it carries a **generated dimension drawing**: the housing (l×b×h) with its light apertures in it, as a top view and a side elevation with dimension lines. `figuurVormen()` computes the shapes once and `figuurSvg()` / `figuurPdf()` render the same list on screen and in the PDF, so the preview cannot drift from the sheet. Dimension arrows flip to the outside when a span is too short to hold them.

A position can have **more than one light aperture, and they need not be centred** — `nieuw.lichtvlakken` is a list of `{l, b, x, y}`, where `x`/`y` are the distance from the left and top edge in the top view. Every field is optional: what is left blank `lichtvlakken()` derives — `RAND` (15 mm) around, the length split evenly over n apertures, and whatever length is left over spread across the n+1 gaps — so emptying a field is also how you hand it back to the tool, and the input's placeholder shows what it then computes. A value that would put an aperture outside the housing is clamped **for the drawing only**; the typed number stays. The drawing keeps its old single dimension line for the common case (one aperture, centred) and switches to a **chain** (edge, aperture, gap, aperture, edge) as soon as there are several or one sits off-centre, so the numbers add up to the length; a segment too narrow for its own number gets only the arrows, which is why `figuurVormen()` takes the renderer's font size. In that same case each aperture also gets its **distance from the top edge**, as a short vertical dimension inside the top view at the aperture's own x — `vertikaal(…, {binnen:true})`, which keeps a short dimension inside its own span instead of letting the arrows stick out, because these start on the edge of the view where the view name sits.

The aperture fields live **under the figure**, in the "Afgeleid figuur" card, not as a row in the intake grid: you type dimensions for something you can see beside them, and the same aperture can be dragged in the drawing (`tekenLichtvlakken()`, called from `tekenAlles()` after `tekenIntake()` has cleared `AFGELEID`).

On screen the apertures are **draggable, one axis at a time, in 5 mm steps** (`SLEEPSTAP`; typing stays free to the millimetre, and the step is applied before the clamp so an aperture can still sit flush against an edge that is not a multiple of 5). Each carries a small two-arrow gizmo drawn by `figuurSvg()` — not by `figuurVormen()`, so it stays off the product sheet, where it would read as part of the drawing. Each axis is its own `<g class="as">` so CSS can scale it on `:hover`, which is how you see which way you are about to pull; the axis being dragged carries `actief`, rendered from `sleep` rather than set as a class afterwards, because the figure is redrawn on every pointermove. Pulling an arrow moves only along that axis; dragging the body picks the axis from the first 3 px of movement, so nothing ever drifts diagonally. The x hit area is **split into two arms** with the crossing point left to y: one rect for both would mean the centre silently belongs to whichever was drawn last. The "centreren" button in each aperture's header empties `x` and `y`, which is the same as never having filled them in — back to the calculated position.

The mechanics: `figuurVormen()` returns `{vormen, kader}`, where `kader` is the px↔mm mapping of the top view, and `figuurSvg()` stores it in `figuurKader` (the SVG renderer, not `figuurVormen` itself — a PDF export would otherwise overwrite it with the sheet's own scale) and marks each aperture rect with `data-vlak`, each grip with `data-as`. The pointer handlers hang on the `<svg>` rather than on the rects, which are replaced on every redraw, and use `getScreenCTM()` so the page's own scaling does not matter. A drag writes rounded millimetres into `x`/`y` — the same thing typing does, so a dragged aperture is simply one with those fields filled in. `ververs()` copies the state back into the input values (not just the placeholders) so the fields follow the drag without rebuilding the grid. A project saved before this carried `nieuw.lichtvlakL`/`lichtvlakB`; `herstelConcept()` moves those into the first aperture and drops the old keys. Which base product a position is built on (`Optic bandraster`, `Flexcore bandraster`, or a typed-in one) is a field; the exact sheet layout is still being worked out.

The **RFQ list** is Distrilight-branded and English, in two forms: a `.xlsx` with the `Bestelformulier` columns for the manufacturer to price, and a PDF (cover-less: header block, summary table, then a spec block per position). `Product Code` and `Unit Price` are editable in the tool as well as in the exported sheet. The `.xlsx` is written by hand — `zipMaak()` builds a store-only (uncompressed) zip so a CRC32 is all the machinery needed, and cells use inline strings so there is no shared-string table. **Don't add a spreadsheet library for this**; the file is one sheet without formulas.

"Project opslaan" uses the same self-baking pattern as `dlc.html`/`armaturenboek.html`: state is baked into a copy of `bandrasters.html` that reopens filled in.

The workbook also carried **in-cell images** at Optiek and Aansluiting — you cannot tell from a name alone which profile or which connector you are picking — so the tool shows a thumbnail under those four dropdowns (click to enlarge). They come from `window.BANDRASTER_BEELDEN` in `bandraster-beelden.js` in the repo root: `{optiek:{naam:dataURI}, aansluiting:{…}}`, data URIs for the same tainted-canvas reason as `armatuur-beelden.js`. A missing file is not an error: the boxes simply stay empty. Each name is its own key — the DALI list repeats the aan-uit connectors with "+ kaal" behind them, and for the Eurosteker and RA-steker that is the same photo but for the GST18-3 variants the workbook has a **separate render with the bare leads in it**, so nothing is folded together; the normalised form only absorbs case and stray spaces. That makes 43 slots (11 optics, 32 connectors) of which 41 carry a photo: the workbook itself leaves "Kaal" and "A-symmetrisch" blank. Photos are stripped from the DOM before "Project opslaan" bakes it: they already live in `bandraster-beelden.js`, which the saved copy reaches through its `<base href>`.

`bandraster-beelden.js` is generated: **`node tools/maak-bandraster-beelden.mjs`** reads `Bandraster_Intake_Nieuw_V3.xlsx` (committed in `docs/bronnen/`) and writes it. In-cell images are not floating drawings — the cell carries a `vm="12"` that runs through `xl/metadata.xml` → `xl/richData/rdrichvalue.xml` → `richValueRel.xml` to a file in `xl/media/`, and the hidden Datasheet pairs those image columns with the name columns, row for row (`AA→AE` and `AD→AE` for the optics, `AH→AI` and `AK→AL` for the connectors — the same columns the Formulier's own XLOOKUPs in E23/L23/E28/L28 use). The script resizes to 440 px and writes **JPEG on white**: the renders come on a transparent background, but they sit on a white card anyway and PNG would make the file seven times bigger (2.4 MB against 0.33 MB for the same 21 images). Names that share a render share one entry, so the file is 0.37 MB for 41 names. Chromium (via Playwright) is used only for that resizing, exactly as the tool's own `leesAfbeelding()` does it. The "Foto's" card in the tool can also write the file, in the same shape — that is the way in for a photo the workbook does not have.
